# ADR-0008: YAML as the config format

**Status**: Accepted
**Date**: 2026-10-03

## Context
The proxy needs a human-editable configuration file that defines routing rules, mirroring targets, and observability settings. The format must be easy to edit by hand, diff cleanly in git, and support nested structures (routes with sub-fields, mirror chains).

## Decision
Use YAML.

## Alternatives Considered

### TOML
- Pros: less ambiguous than YAML, better for flat configs, well-defined spec.
- Cons: awkward for deeply nested structures like route lists with per-route options. The config has more nesting than TOML handles comfortably.

### JSON
- Pros: universal, unambiguous, easy to generate programmatically.
- Cons: no comments, verbose, painful to edit by hand. Rejected for a hand-edited config.

### Custom DSL
- Pros: could match domain concepts exactly.
- Cons: massive overkill, requires parser and tooling, high maintenance cost.

## Consequences
**Positive:**
- Human-readable and human-editable.
- Ubiquitous.
- Nested structures (routes, mirror chains) map cleanly.

**Negative:**
- YAML has well-known footguns: type coercion (`yes` → bool, `1.0` → float), anchors/aliases that can surprise, significant whitespace.
- Spec is long and implementations differ; we use one library consistently.

**Technical debt:**
- None intended. If YAML footguns cause real problems in practice, consider TOML, JSON or other stricter language. 

## Revisit Triggers
- Repeated bugs caused by YAML type coercion.
- Need for config schema validation beyond what our current validator does.
